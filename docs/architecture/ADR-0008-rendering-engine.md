# 1. Purpose

This ADR defines the architecture of the Rendering Engine.

The Rendering Engine SHALL be responsible only for displaying the CAD
scene.

Rendering MUST remain completely independent from geometry creation,
constraint solving and history management.

The Rendering Engine SHALL consume immutable scene data generated by
the CAD Kernel.

---

# 2. Scope

The Rendering Engine SHALL manage:

- Scene rendering
- Camera
- Viewport
- Grid
- Selection highlighting
- Object visibility
- Rendering layers
- GPU resource management
- Frame synchronization

Future versions MAY support:

- Vulkan
- Physically Based Rendering
- Ray Tracing
- Shadows
- Ambient Occlusion
- HDR Rendering

---

# 3. Non-Goals

The Rendering Engine MUST NOT:

- Solve constraints
- Generate geometry
- Modify project data
- Store history
- Manage files
- Perform boolean operations

---

# 4. Definitions

Scene

The collection of renderable objects.

Viewport

Visible drawing region.

Camera

Defines projection and view matrices.

Renderer

The subsystem responsible for drawing a frame.

Render Object

GPU-ready representation of CAD entities.

---

# 5. Problem Statement

Modern CAD applications require smooth interaction.

Rendering thousands of entities every frame can become expensive.

The rendering system therefore needs:

- Incremental updates
- GPU acceleration
- Cached geometry
- Layer-based rendering
- Efficient culling

---

# 6. Decision

Rendering SHALL be implemented as an independent subsystem.

It SHALL receive scene updates exclusively from the CAD Kernel.

No rendering code SHALL exist inside Sketch, Constraint or Dimension
engines.

# 14. Camera System

The camera SHALL support:

- Pan
- Zoom

---

# 15. Performance Objectives

The Rendering Engine SHOULD:

- Sustain 120 FPS on supported hardware.
- Minimize CPU-GPU synchronization.
- Cache static geometry.
- Use frustum culling where applicable.
- Avoid unnecessary redraws.

# 16. Public API

The Rendering Engine SHALL expose its functionality through the CAD
Kernel only.

The public API MUST remain backend-independent.

Required API capabilities:

- Create Scene
- Update Scene
- Remove Render Object
- Invalidate Layer
- Render Frame
- Resize Viewport
- Set Camera
- Request Redraw

Rendering backends MUST implement the same abstract interface.

---

# 17. Resource Management

GPU resources SHALL be managed centrally.

Managed resources include:

- Vertex Buffers
- Index Buffers
- Texture Resources
- Shader Programs
- Font Atlases
- Frame Buffers

Unused resources SHOULD be released automatically.

The engine SHALL support lazy resource creation.

---

# 18. Rendering States

The renderer SHALL maintain explicit rendering states.

Example:

```text
Renderer State
│
├── Idle
├── Preparing Frame
├── Updating Buffers
├── Rendering
├── Presenting
└── Recovering
```

Only one rendering state MAY be active at any given time.

---

# 19. Selection Rendering

Selection SHALL be rendered separately from geometry.

Pipeline:

```text
Scene
 │
 ▼
Geometry Pass
 │
 ▼
Selection Pass
 │
 ▼
Overlay Pass
 │
 ▼
Present
```

Selection highlighting MUST NOT modify original geometry.

# 21. Graphics Backend Abstraction

```text
                 Rendering Engine
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
 Compose Backend   OpenGL Backend   Vulkan Backend
```

Backends SHALL implement a common interface.

The Rendering Engine MUST remain unaware of backend-specific APIs.

---

# 22. Error Handling

The renderer SHALL detect and report:

- Invalid GPU resources
- Shader compilation failures
- Buffer allocation failures
- Unsupported hardware features
- Lost rendering context

Rendering errors MUST NOT corrupt project data.

The renderer SHOULD recover automatically whenever possible.

---

# 23. Security Considerations

The Rendering Engine SHALL validate all incoming scene data.

Malformed geometry MUST NOT cause undefined behavior.

Future plugin-provided render objects SHALL be sandboxed through the
CAD Kernel.

---

# 24. Risks

Potential risks:

- GPU memory exhaustion
- Backend incompatibilities
- Large scene performance degradation
- Driver-specific rendering bugs
- Resource leaks

Mitigation strategies:

- Resource pooling
- Incremental rendering
- Backend abstraction
- Automated performance tests
- Continuous profiling

---

# 31. Decision Summary

The Rendering Engine is adopted as an isolated subsystem dedicated to
scene visualization.

It SHALL consume immutable scene data from the CAD Kernel and SHALL NOT
perform geometry generation, constraint solving, or project management.

A backend abstraction layer ensures long-term flexibility, allowing
multiple graphics APIs to be supported without changing the public
Rendering Engine interface.
